# V4 模拟盘包（Polymarket BTC 五分钟涨跌）

**只做纸面交易，结构上不可能下单。** 本包内没有私钥、没有签名、没有下单接口，
所有行情调用都是公开只读 GET。

---

## 一、这是一个什么策略

在 5 分钟窗口走过 **120 秒**（即收盘前 180 秒）时决策。三个条件同时成立就顺着方向买入，持有到结算：

| 条件 | 阈值 | 作用 |
|---|---|---|
| **① 订单簿一边倒** | \|买卖失衡\| ≥ **0.30** | **核心优势** |
| ② 代币动过 | Up 代币相对开盘移动 ≥ **0.20** | 有方向 |
| ③ 现货也动过 | BTC 相对开盘移动 ≥ **4.5bps** | 排除无支撑报价 |

**方向**：Up 代币涨 → 买 UP；跌 → 买 DOWN。**没有止盈，没有止损。**

### 为什么"订单簿一边倒"是核心

账面（买盘 vs 卖盘的总名义价值）如果平衡，代币的移动就**没有委托流支撑**，那些交易是噪声，亏得很惨。实测按移动幅度分档：

| 移动幅度 | 账面平衡 | **账面一边倒** |
|---|---|---|
| 0.20–0.30 | **−9.59%** | **+11.07%** |
| 0.30–0.40 | **−7.54%** | **+5.33%** |
| 0.40–0.55 | **−5.61%** | **+1.67%** |

**每一档都是右边赢** —— 这是独立信息，不是已有信号的化身。

**没有这个过滤，策略是亏的**（市场定价公允，0.07 手续费吞掉全部优势）。

## 二、实测表现（44 天 / 12,670 个市场）

训练 22 天、样本外 22 天。

| 数据块 | 天数 | 胜率 | 进场价 | **每份收益** | 为正天数 |
|---|---|---|---|---|---|
| 训练 | 22 | 93.4% | 0.867 | +5.88% | **22/22** |
| **规则声明后新增的 7 天** | **7** | **93.3%** | 0.865 | **+5.95%** | **7/7** |
| 样本外 旧（05-01~17） | 15 | 93.9% | 0.879 | +5.31% | 15/15 |
| 样本外 新（05-18~24） | 7 | 93.0% | 0.881 | +4.21% | 6/7 |
| **样本外汇总** | **22** | **93.6%** | **0.880** | **+4.96%** | **21/22** |
| 样本外（**关掉过滤**） | 22 | 87.2% | 0.864 | **+0.05%** | 10/22 |

**2σ 区间 +3.92% ~ +5.95%，排除零。**

**关掉过滤只剩 +0.05%（96 倍差距）** —— 因果清楚。

## 三、入场时点很重要：越早越好

胜率几乎不变，但**价格差很多**：

| 时点 | 窗口内 | 样本外每天 | 笔/天 | 进场价 | 为正天数 |
|---|---|---|---|---|---|
| **T-240** | 60 秒 | **+8.68%** | 26 | **0.819** | 21/22 |
| T-210 | 90 秒 | +6.29% | 41 | 0.853 | 21/22 |
| **T-180（当前默认）** | **120 秒** | **+4.93%** | 52 | 0.880 | 21/22 |
| T-150 | 150 秒 | +3.87% | 62 | 0.900 | 21/22 |
| T-120 | 180 秒 | +0.77% | 71 | 0.928 | **14/22** ⚠️ |

**T-240 期望最高但每天只有 26 笔**，所以默认 T-180 平衡收益和样本量。

**这是纸面跟踪期间唯一值得试的参数**：

```bash
python run_live_v4.py run --entry-t-minus 240
```

或改 `config_v4/strategy_v4.json` 的 `entry_t_minus`。

## 五、怎么用

### 先自检（不需要网络）

```bash
cd v4
python run_strategy_v4.py selfcheck          # 期望 36/36
python run_strategy_v4.py outlook --stake 10 # 实盘预期（含入场时点对比）
```

### 第 1 步：验证行情源（**必须先做**）

```bash
python run_live_v4.py probe
```

> ⚠️ **`engine_v4/feed.py` 从未在真实网络下运行过。**
> 它是在**没有外网的环境**里写的，所有 URL 和字段名都来自文档而非实测响应。
>
> `probe` 会抓一个市场和一本盘口并打印原始内容 —— **字段名若有变化会立刻暴露**，
> 而不是在凌晨三点静默失败。**probe 不通过就不要开跑。**

### 第 2 步：跑纸面交易

```bash
python run_live_v4.py run --stake 10
python run_live_v4.py run --stake 10 --seconds 3600      # 限时
python run_live_v4.py run --entry-t-minus 240            # 试更早的时点
```

### 第 3 步：看报告

```bash
python run_live_v4.py report
```

### 可选：离线复验（需要数据集）

```bash
python tools_v4/build_cache.py        # 一次性，~8 分钟，约 1.3 GB
python tools_v4/parity_check.py       # 必须 0 failures
python tools_v4/review.py             # 必须 22/22
python tools_v4/imbalance_final.py    # 核心验证结果
```

数据集若不在默认位置，用 `--root <路径>` 或设 `V4_DATA_ROOT`。
`tools_v4/paths.py` 会自动在几个候选位置查找，找不到会明确报错并告诉你怎么做。

## 六、纸面跟踪要盯的 5 个数字

按重要性排序（`config_v4/strategy_v4.json` 的 `LIVE_CHECKS` 有完整说明）：

| # | 指标 | 容忍度 | 为什么 |
|---|---|---|---|
| **1** | **决策到成交的价差（延迟漂移）** | **中位 ≤3 分钱** | 回测假设按报价成交，**这个差距决定实盘盈亏** |
| **2** | **实时盘口 notional vs 数据集** | 同数量级 | 若是浅层视图，**0.30 阈值含义就变了** |
| 3 | 现货报价新鲜度 | 尽量新 | 4.5bps 是小移动，**过期价格会误判** |
| 4 | 拒绝原因分布 | 稳定 | 突变说明行情源或市场变了 |
| 5 | 实际成交频率 | 约 52 笔/天 | 远低说明闸门异常触发 |

`report` 会打印第 1 项的中位数和 p90 —— **这是唯一还没实测的关键数字。**

## 七、熔断条件（开跑前先定好）

写在 `config_v4/strategy_v4.json` 的 `KILL_CRITERIA`，任一成立就停：

- 延迟漂移中位 **> 3 分钱**
- 实时盘口 notional 与数据集差几个数量级（失衡闸门不可信）
- 实际频率 **< 17 笔/天**（预期 52 的三分之一）
- 累计 30 笔以上结算后**胜率 < 90%**

## 八、必须知道的限制

1. **本包不能下单。** 没有私钥、没有签名、没有下单接口 —— 这是结构性的，不是开关。
2. **`feed.py` 未经实测。** 见第五节第 1 步。
3. **失衡这个"想法"是在同一数据集上形成的。** 阈值 0.30 是**事前登记**的
   （声明后才到的 7 天返回 +5.95%、7/7 为正），所以**对阈值**是干净的样本外，
   **对假设本身**不是完全独立。
4. **手续费 0.07 已确认**（Crypto 类目 taker）。盈亏平衡费率是 0.053 ——
   是因为失衡过滤带来了足够优势才覆盖住。
5. **成交价需实测。** 回测按报价算；实盘能否拿到那个价，是纸面跟踪要回答的问题。
6. **数据文件不在本包内。** 本包只含代码（约 250 KB）。

## 九、开发中发现并修掉的两个真实缺陷

记录在此，因为它们说明了为什么这些检查工具是必要的。

### 缺陷一：缓存索引映射错误（决策点偏移 57 秒）

快速缓存读取器把倒计时索引映射到了 tick 列表的**错误一端**
（`_deadlines` 升序而 `ticks` 是时序降序，两个列表用同一个下标）。
结果是 **T-120 实际取到了 T-178 的报价**。

**它返回的是真实价格，不报错、不崩溃，所有下游数字都接受了它。**
前两轮"样本外验证"全部跑在这个错误时点上。

修复后重跑，反而发现**越早入场越好**（第三节那张表）。

→ `tools_v4/parity_check.py` 就是为此存在：**缓存只有在被证明等于它所缓存的东西之后才是安全的。**

### 缺陷二：验证工具的参数漂移

验证脚本把入场时点**硬编码**为 T-120。当策略改为 T-180 后，
脚本仍然验证 T-120，**打印出不再描述该策略的数字**。

→ 现在所有验证工具的参数都**从 `V4Params()` 读取**，两者不可能再漂移。

### 顺带修掉的测试自身缺陷

- `review.py` 用「tick 在磁带中的位置比例」判断时点是否正确 ——
  **tick 在时间上并非均匀分布**（安静时段行数少），这个比例不对应时间。
  已改为直接检查**倒计时的实际数值**（现在中位偏差 31ms）。
- 测试里写死「移动 0.20」当作"强信号"，门槛升到 0.20 后就越界了。
  已改为**由门槛推导**。
- 手续费对称性用了浮点精确相等 —— `f(0.7)` 与 `f(0.3)` 差 3e-18。
  已改为容差比较。

**这些都不是策略缺陷，但它们会让检查结果说谎。**
