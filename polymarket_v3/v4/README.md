# V4 模拟盘包（Polymarket BTC 五分钟涨跌）

**只做纸面交易，结构上不可能下单。** 本包内没有私钥、没有签名、没有下单接口，
所有行情调用都是公开只读 GET。

---

## 一、这个策略在做什么

在 5 分钟窗口走过 180 秒时，同时满足三个条件就顺着方向买入，持有到结算：

| 条件 | 阈值 | 作用 |
|---|---|---|
| **① 代币动过** | Up 代币相对开盘移动 ≥ **0.20** | 有方向 |
| **② 订单簿一边倒** | \|买卖失衡\| ≥ **0.30** | **核心优势** |
| ③ 现货也动过 | BTC 相对开盘移动 ≥ **4.5bps** | 排除无支撑的报价 |

方向：Up 代币涨 → 买 UP；跌 → 买 DOWN。**没有止盈，没有止损。**

### 为什么是"订单簿一边倒"

如果账面是平衡的，代币的移动就没有委托流支撑，那些交易是噪声，**亏得很惨**。
实测（按移动幅度分档对比）：

| 移动幅度 | 账面平衡 | **账面一边倒** |
|---|---|---|
| 0.20–0.30 | **−9.59%** | **+11.07%** |
| 0.30–0.40 | **−7.54%** | **+5.33%** |
| 0.40–0.55 | **−5.61%** | **+1.67%** |

**每一档都是右边赢** —— 说明这是独立信息，不是已有信号的化身。

**没有这个过滤，策略是亏的**（市场定价公允，手续费吞掉全部优势）。

## 二、实测表现

44 天 / 12,670 个市场，训练 22 天、样本外 22 天。

| 数据块 | 天数 | 胜率 | **每份收益** | 为正天数 |
|---|---|---|---|---|
| 训练 | 22 | 93.4% | +5.88% | 22/22 |
| **规则声明后新增的 7 天** | **7** | **94.3%** | **+6.15%** | **7/7** |
| **样本外合计** | **22** | **93.6%** | **+4.93%** | **21/22** |
| 样本外（**关掉过滤**） | 22 | 87.1% | **−0.02%** | 9/22 |

**2σ 区间 +4.00% ~ +5.86%，排除零。**

### 滑点容忍度（最关键的改善）

| 额外成本 | 每份收益 | 10 USDC 每天 |
|---|---|---|
| 实测 | +4.76% | +28 |
| +1 分 | +3.81% | +22 |
| **+2 分** | **+2.87%** | **+16** |
| +3 分 | +1.96% | +11 |

**加 3 分钱滑点仍盈利。**（旧配置加 2 分钱就归零。）

## 三、入场时点很重要，越早越好

胜率几乎不变，但**价格差很多**：

| 时点 | 样本外每天 | 笔/天 | 进场价 | 为正天数 |
|---|---|---|---|---|
| **T-240** | **+8.68%** | 26 | 0.819 | 21/22 |
| T-210 | +6.29% | 41 | 0.853 | 21/22 |
| **T-180（当前默认）** | **+4.93%** | 52 | 0.880 | 21/22 |
| T-150 | +3.87% | 62 | 0.900 | 21/22 |
| T-120 | +0.77% | 71 | 0.928 | 14/22 ⚠️ |

**T-240 期望最高但每天只有 26 笔**，所以默认用 T-180 平衡收益和样本量。
**这是纸面跟踪期间唯一值得试的参数** —— 改 `config_v4/strategy_v4.json` 里的
`entry_t_minus`，或加命令行参数。

## 五、怎么用

### 第 0 步：先自检（不需要网络）

```bash
cd v4
python run_strategy_v4.py selfcheck     # 期望 36/36
python run_strategy_v4.py outlook --stake 10
```

### 第 1 步：验证行情源（**必须先做**）

```bash
python run_live_v4.py probe
```

> ⚠️ **`engine_v4/feed.py` 从未在真实网络下运行过** —— 它是在没有外网的环境里写的，
> 所有 URL、字段名都来自文档而非实测响应。
> `probe` 会抓一个市场和一本盘口并打印原始结果，**如果字段变了会立刻暴露**，
> 而不是在凌晨三点静默失败。
>
> **probe 不通过就不要开跑。**

### 第 2 步：跑纸面交易

```bash
python run_live_v4.py run --stake 10
# 或限时
python run_live_v4.py run --stake 10 --seconds 3600
# 试其他入场时点
python run_live_v4.py run --entry-t-minus 240
```

### 第 3 步：看报告

```bash
python run_live_v4.py report
```

## 六、纸面跟踪要盯的 5 个数字

按重要性排序（`config_v4/strategy_v4.json` 的 `LIVE_CHECKS` 有完整说明）：

| # | 指标 | 容忍度 | 为什么 |
|---|---|---|---|
| **1** | **决策到成交的价差（延迟漂移）** | **中位 ≤3 分钱** | 回测假设按报价成交，**这个差距决定实盘盈亏** |
| **2** | **实时盘口 notional vs 数据集** | 同数量级 | 若实时盘口只是浅层视图，**0.30 这个阈值含义就变了** |
| 3 | 现货报价新鲜度 | 尽量新 | 4.5bps 是小移动，**过期价格会让这个闸门误判** |
| 4 | 拒绝原因分布 | 稳定 | 突然变化说明行情源或市场变了 |
| 5 | 实际成交频率 | 约 52 笔/天 | 远低于此说明闸门异常触发 |

`report` 会打印第 1 项的中位数和 p90 —— **这是本项目唯一还没实测的关键数字。**

## 七、熔断条件（开跑前先定好）

`config_v4/strategy_v4.json` 的 `KILL_CRITERIA`，任一成立就停：

- 延迟漂移中位 **> 3 分钱**
- 实时盘口 notional 与数据集差几个数量级（失衡闸门不可信）
- 实际频率 **< 预期 52 笔/天的三分之一**
- 累计 30 笔以上结算后**胜率 < 90%**

---

## 八、必须知道的限制

1. **本包不能下单。** 没有私钥、没有签名、没有下单接口 —— 这是结构性的，不是开关。
2. **feed.py 未经实测。** 见第五节第 1 步。
3. **失衡这个"想法"是在同一数据集上形成的。** 阈值 0.30 是**事前登记**的
   （声明后才到的 7 天返回 +6.15%、7/7 为正），所以对阈值是干净的样本外，
   但对假设本身不是完全独立。
4. **手续费 0.07 已确认**（Crypto 类目 taker）。盈亏平衡费率是 0.053，
   所以这个费率是真实的成本压力 —— 只是在失衡过滤之后被覆盖了。
5. **成交价需实测。** 回测按报价算；实盘能否拿到那个价，是纸面跟踪要回答的问题。

### 一次真实的数据缺陷教训

开发过程中，快速缓存读取器把倒计时索引映射到了 tick 列表的错误一端，
导致实际决策时点偏移了 **约 57 秒**（T-120 实际在 T-178）。
**它返回的是真实价格，所有下游数字都接受了它，没有任何报错。**

`tools_v4/parity_check.py` 就是为此存在：**缓存只有在被证明等于它所缓存的东西之后才是安全的。**
修复后重跑，才发现"越早入场越好"这个更强的结论。

## 九、复现验证（可选，需要数据）

离线复验需要 `micro_v3` 数据目录：

```bash
python tools_v4/build_cache.py          # 一次性，~8 分钟，约 1.3 GB
python tools_v4/parity_check.py         # 必须 0 failures
```

`parity_check.py` 拿缓存和权威加载器逐市场比对每个时点的 tick —— **这个测试如果不过，通过缓存得到的任何数字都不可信。**
