## 1. 数据概况（实测，非推测）

37 个 parquet 文件全部由 **DuckDB v1.4.4** 写出，分布在 5 种 schema：

| 子集 | 文件数 | 行数 | 列名（实测） |
|---|---|---|---|
| **orderbooks** | 13 | **3,208,877** | `timestamp, asset, market_id, condition_id, token_id, question, best_bid, best_ask, spread, mid_price, bid_levels, ask_levels` |
| **trades** | 4 | **3,722,171** | `timestamp, asset, market_id, condition_id, token_id, side, price, size, tx_hash, maker, source` |
| **crypto_prices** | 13 | **67,452** | `timestamp, asset, open, high, low, close, volume, trade_count` |
| **price_history** | 4 | **149,769** | `timestamp, asset, market_id, token_id, price` |
| **resolution** | **2** | **28,016 + 27,332** | `market_id, asset, condition_id, question, start_time, end_time, resolved_at, outcome` |

**36 个文件、合计 7,203,617 行、约 247 MB。** 注意 resolution 有**两份**（`all.parquet` 与 `all (1).parquet`，28,016 与 27,332 行）——它们高度重叠但不完全相同，**用哪一份会影响覆盖率，需要你自己确认哪个是权威版本**；我的代码会把两份都读入并按 `market_id` 覆盖，后读的赢。

关键点：

* **时间类型是 TIMESTAMP 原生类型**（不是 epoch 数字），所以**不存在"秒还是毫秒"的歧义**——这省掉了这类数据最大的一个坑。
* **盘口只有 token_id，没有 outcome 字段**；UP/DOWN 只能通过 `resolution.outcome` + 末期价格高低推断。我在代码里对"两侧价格接近、无法判断"的市场**直接跳过并计数**，绝不猜。
* `bid_levels` / `ask_levels` 是 **BSON**（DuckDB 的列表列），不是 JSON 文本；解析要能吃 bytes。已处理。
* `resolution` 有 28,016 个市场的 `end_time` 与 `outcome`——**这是整条策略的地面真值**，有了它才能做有意义的优化。
* ⚠️ **文件里有重复下载的副本**：`2026-03-11 (1).parquet`（91.8 MB / 201 万笔成交）、`2026-03-19 (1).parquet`（60.4 MB / 137 万笔）、以及一批 `(1)(2)(3)` 后缀的小文件。它们和时间戳无后缀的文件内容重叠，**去重前统计会把量算大**。

## 2. 最重要的一条结论：**在你这份数据里，"锁利"机会根本不存在**

我拿到了可用环境后，**直接在你的真实数据上跑了**（`tools/check_lock_opportunities.py`，2026-03-02 全天 orderbooks）。这不是推测，是实测：

```
rows read            : 308,370
markets with books   : 1,548
markets paired       : 347
paired checkpoints   : 3,940

UP+DOWN ask sum（窗口最后 180 秒内、两侧逐秒配对）:
  min    1.0200      p5   1.6400      median 1.8000      max 1.9490

每个市场在最后 180 秒内出现过的最低 sum:
  min    1.0200      p5   1.3900      median 1.8000

锁利可行性（保本 sum ≈ 0.9650~0.9687）:
  sum <= 0.95 :   0 个检查点 (0.00%)    0 个市场 (0.00%)
  sum <= 1.00 :   0 个检查点 (0.00%)    0 个市场 (0.00%)
```

**没有任何一个市场、任何一个时刻，UP+DOWN 的卖一之和低于 1.00。** 最低是 XRP 的 1.02。

### 为什么？因为这份数据的盘口极宽

| 指标（296,263 个快照） | 值 |
|---|---|
| 价差中位数 | **0.800** |
| 价差 ≤ 0.05 的占比 | **0.00%** |
| 价差 ≥ 0.50 的占比 | **99.77%** |
| 最常见盘口 | `bid 0.10 / ask 0.90`（占 66.4%） |

我起初怀疑这是解析错误，所以逐层验证了：

* 阶梯与摘要列**完全一致**（0% mismatch）；
* 阶梯内部自洽：买盘 0.01~0.10、卖盘 0.90~0.99；
* **极端价位有真实深度**：0.01 挂 18,759 份、0.99 挂 18,886 份；卖一 0.90 有 1,349 份；
* 所以我之前担心的"解析错了"不成立——**这确实是真实盘口**；
* 旁证：`trades` 表里 33 万笔成交价格分布正常（中位 0.53，50% 落在 0.30~0.70），说明成交数据没问题，**是盘口本身一直很宽**。

**含义（这是本次分析最重要的结论）**：

> 你的策略入场条件 `UP + DOWN ≤ 0.95` 在这份数据上**触发率为 0**。
> 因此**调 `movePct` / `windowMin` / `sumTarget` 不可能"优化"出收益**——这不是参数问题，
> 是**策略前提在这批数据上不成立**。`sumTarget` 设成 0.98、0.99、甚至 1.00 都一样是 0 次触发。

另外注意：**1,548 个有盘口的市场里只有 347 个成功配对**。说明相当一部分市场**只有单边有快照**——
如果你想做双边锁利，连"两边同时有报价"这个前提都常常不满足。这本身就是执行层面的硬约束。

### 那"5 分钟"和"后续月份"呢？

本文件是 **15 分钟窗口**（slug 形如 `btc-updown-15m-...`）。5 分钟窗口的盘口通常更宽（时间更短、更少人做市），
所以锁利机会**只会更少**，不会更多。同时我这次只跑了 **1 天**（2026-03-02）——严格来说应该把 13 天全跑一遍再下最终结论。
把这条命令对每个文件跑一遍即可（几分钟一个文件）：

```bash
python tools\check_lock_opportunities.py --file "..\data\2026-03-03.parquet"
```

如果 13 天全是 0 触发，那么结论就非常硬：**这条路走不通**，应该转向做市/挂单收价差（利用这 0.80 的宽价差），
而不是等一个不会出现的套利机会。

## 3. 第二个结论：**你现在的对冲结构本身也不是锁利**

即便将来真的出现 sum < 0.965 的机会，用**"两边各买相同 USDC"**也锁不住。这是我写回测时被测试抓出来的（详见第 6 节留档）。

假设出现 UP 卖一 0.30、DOWN 卖一 0.60（sum=0.90），两边各投 100 USDC：

| 结算分支 | 买到份额 | 结算收入 | 总成本 | 盈亏 |
|---|---|---|---|---|
| UP 赢 | 100/0.30 = 333.3 | 333.3 | ~200.6 | **+125.6** |
| DOWN 赢 | 100/0.60 = 166.7 | 166.7 | ~200.6 | **−41.0** |

**sum=0.90 完全没有锁住任何东西**：DOWN 赢的那一支亏 41。因为等额法买到的份额不一样（越便宜买得越多），
盈亏完全取决于**哪一边赢**——这是方向性下注，不是套利。

### 真正的锁利：**两边买相同份额**

若两边各买 **N 份**，无论谁赢都收 N：

```
总成本 = N × (ask_up + ask_down) + 手续费
保证盈利  ⟺  ask_up + ask_down + 每份手续费 < 1
```

在 0.30/0.60 上买 N=1：成本 0.90 + 手续费 0.0315 = 0.9315，收 1.0，**锁定 0.0685**（两边完全一样，测试已断言 `pnl_if_up == pnl_if_down`）。

**你的 `sumTarget=0.95` 本身是合理阈值**——保本线实测在 **0.9650~0.969**（下表），0.95 留了约 1.5 分安全边际：

| 盘口比例 | 保本 sum（精确求解） | sum=0.95 时每份净利 |
|---|---|---|
| 0.30 / 0.60 | 0.9687 | +0.0186 |
| 0.40 / 0.50 | 0.9654 | +0.0155 |
| 0.45 / 0.45 | 0.9650 | +0.0151 |
| 0.50 / 0.50 | 0.9650 | +0.0151 |

所以问题**不在阈值高低**，而在于：**这个阈值在你的数据里永远等不到**（第 2 节）。
以及**每份利润只有 1.5~1.9 分**——两条腿滑点合计超过 1.5 分（150bps）就从赚变亏，**滑点才是生死线**。

## 4. 另外两个默认参数的问题

### `movePct = 0.15`

**单位存疑，且大概率写错了。** 15% 是三秒内的巨幅波动，BTC 几乎不可能出现；如果你原意是 **0.15%（=0.0015）**，那写法差 100 倍。我在回测里按"百分数"处理（`0.15` 表示 0.15%），网格会同时扫 `0.02 / 0.05 / 0.10 / 0.15 / 0.30 / 0.50`，让数据告诉你哪个阈值有效——**但你必须先确认原始代码里这个数的单位**。

另外，"3 秒内跌 15%"这种口径在预测市场监管上也值得怀疑：现货在 3 秒内动 15%，更可能是**数据错误或极端插针**，而不是可交易信号。建议改为**多窗口**：3 秒（毫秒级噪声）、60 秒、剩余窗口（1~2 分钟）三个口径都算，再比较哪个与结算结果相关性最高。

更重要的一点：**这个策略其实不需要 `movePct`**。锁利条件只看 `sum_ask` 是否低于保本线——现货跌多少并不进入盈亏公式。`movePct` 只该用来**过滤"为什么便宜"**（是真恐慌抛售，还是市场知道了你不知道的事）。所以它的作用是风控筛子，不是收益来源。

### `windowMin = 2`

方向合理但要扫。逻辑上：越靠近结算，同样幅度的现货位移越"决定性"（信息量越大）；但越晚进场，盘口越薄、滑点越大、留给对冲的时间越少。这是一组明确的权衡，**必须用真实盘口在 T-60/-30/-15/-5 分别算清**，不能拍。我默认扫 `240/180/120/90/60/45/30/20/15/10/5`。

注意：对**锁利**策略而言，晚进场的边际收益来自"命中率"（此刻 sum 是否更常低于保本线），边际成本来自"滑点"（盘子更薄）。`timing_sweep.csv` 会同时给出这两项。

## 8. 实盘前必须改的参数（按优先级，已按修正后的计算更新）

| 优先级 | 参数 | 现在 | 改成 | 理由 |
|---|---|---|---|---|
| 🔴 P0 | **对冲方式** | 两边买相同金额 | **两边买相同份额**（`mode="lock"`） | 等额法在 DOWN 赢的分支亏 41（实测），根本不锁利 |
| 🔴 P0 | **滑点控制** | 未提及 | 每条腿滑点合计 **< 1.5 分（150bps）**，否则从赚变亏 | 每份利润只有 1.5~1.9 分，滑点就是生死线 |
| 🟠 P1 | `movePct` | `0.15` | 先确认单位；按 % 理解则为 0.15%，扫 0.02~0.50 | 单位差 100 倍会让信号不触发或狂触发；且它只该当风控筛子，收益不依赖它 |
| 🟠 P1 | `windowMin` | `2` | 用 `timing_sweep.csv` 定，候选 T-60/-30/-15 | 晚进场命中率↑但滑点↑，必须实测权衡 |
| 🟢 P2 | `sumTarget` | `0.95` | **保持 0.95**（别超过 0.96） | 保本线 0.965~0.969，0.95 留有 1.5 分安全边际 |
| 🟡 P2 | 成交前检查 | 无 | 加：**昂贵腿的可见深度** ≥ 目标份额 | 锁利单需两条腿都成交，一腿失败就变成裸方向仓 |
| 🟡 P2 | 数据去重 | 无 | 排除 `(1)(2)(3)` 重复文件 | 否则统计量虚高 |

**最后一句提醒**：真正的锁利机会要求 `ask_up + ask_down < 0.965`。如果这个条件在你的历史数据里**很少出现**（完全可能——这类机会通常会被机器人秒掉），那么正确的结论不是"调参"，而是**这个策略方向本身不成立**，应该转向做市/流动性提供。`opportunities.csv` 会直接告诉你答案：里面有每一次机会的 `sum_cost`、`winner`，以及**廉价那条腿最后是否真的赢了**（`cheap_won`）——如果 `cheap_won` 显著低于 50%，说明"便宜"是因为市场知道它会输，那就是在接飞刀。
