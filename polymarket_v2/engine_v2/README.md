# Polymarket 末段动量狙击引擎 (v2.0)

**这就是替代原有玩法的完整实现。** 原有设计（等价格暴跌 → 买暴跌方 → 反向对冲锁 UP+DOWN ≤ 0.95）在你的真实数据上**从未成立过**：见附录 A。本引擎实现的是数据支持的版本。

```
polymarket_sniper/
├── run_engine.py           ← 唯一入口
└── engine/
    ├── config.json         全部可调参数（含"为什么是这个值"的注释）
    ├── config.py           类型化配置 + 启动即校验
    ├── dataio.py           parquet 读取、市场/结果合并、as-of 价格索引
    ├── signals.py          动量信号（只允许回看，不允许前视）
    ├── guards.py           执行闸门：报价陈旧 / 滑点 / 深度 / 价格带
    ├── broker.py           模拟盘 + 实盘边界（默认拒绝实盘）
    ├── mathx.py            手续费与盘口阶梯数学
    ├── backtest.py         回测引擎（逐笔顺序判定 TP/SL）
    └── cli.py              命令行
```

## 一、策略逻辑（为什么是这些规则）

### 1. 核心思想：末段动量延续

在 5/15 分钟的 Up-or-Down 窗口里，如果**标的在过去几分钟已经明确移动**，这个移动倾向于延续到结算。所以：

* **T-120 秒**做决策（不是 T-10 秒）
* 用 **180 秒回看窗口**测量标的位移
* 位移超过 **0.05%** 才动手
* 买标的移动的那个方向

### 2. 为什么入场点是 T-120 而不是 T-10

**因为你的数据里 T-30 及以后根本没有成交记录**：T-120 有 466 笔可用、T-60 有 373 笔、**T-30 / T-15 / T-5 全是 0**。

原设计叫"末秒狙击"，但在这批数据上 T-30 以内**既无法回测也无法验证**。引擎默认 T-120，这是"能被证据支持的最晚时点"，不是"理论上最好的时点"。等你有更细的数据（orderbooks 有 1.8 秒粒度快照）再往 T-60 以内推进。

### 3. 方向准确率随回看窗口单调上升（这是最重要的一条）

| 回看窗口 | 方向准确率 |
|---|---|
| 60 秒 | 62.7% |
| 120 秒 | 67.1% |
| **180 秒** | **73.1%** |
| 300 秒 | 75.9% |

所以 `lookback_s` 比 `entry_t_minus_s` 更值得调。但要说清本质：**180 秒回看在 900 秒窗口里读的是"窗口早期动量"，不是"末秒结构"**——这实质上是一个动量策略，名字里的 "endgame" 是它的入场时机，不是它的收益来源。

### 4. 止盈/止损：为什么是 +0.30 / −0.20

在真实成交上跑完整网格（TP 与 SL **同时挂着**、逐笔按价格顺序判定先碰到谁）：

| TP | SL | 组合净利 | 胜率 | 最大回撤 |
|---|---|---|---|---|
| **0.10** | **0.05（原设计）** | **2,808** | 62.7% | 1,815 |
| 0.30 | 0.05 | 18,915 | 54.2% | 1,065 |
| 0.30 | 0.10 | 24,477 | 64.8% | 851 |
| **0.30** | **0.20** | **28,967** | 72.7% | **866** |
| — 不挂，持到结算 | — | 28,597 | 72.8% | 1,279 |

两条反直觉但实测的结论：

* **止盈越紧越亏。** 这是**二元结算**市场，获胜方向终值本来就是 **1.0**；在 0.62 止盈等于白让 0.38，而 TP=0.10 的触发率高达 80.5%——绝大多数赢单被提前掐断。
* **止损越紧越亏。** SL=0.05 在组合口径下触发率 32.3%，净利只有 2,808；放宽到 0.20 后触发率降到 16.0%，净利 28,967，**回撤还更低**。紧止损是"在噪声里割肉"，把本来会结算成 1.0 的单子砍在低位。

### 5. 执行闸门：报价陈旧是最致命的实盘陷阱

| 最后一笔成交距今 | 笔数 | 方向准确率 | 净利 |
|---|---|---|---|
| ≤ 10 秒 | 774 | **76.0%** | **+4,723** |
| > 10 秒 | 65 | **35.4%** | **−1,915** |

**陈旧报价的方向准确率只有 35.4%，比抛硬币还差，而且吃掉了全部亏损。**

原因很直白：当最新成交是 30 秒甚至 209 秒前，你读到的"现货已确认方向"是一个**已经作废的价格**，此时下单等于随机下注。所以 `max_quote_staleness_s = 10` 是本引擎**最值钱的一个参数**，比任何 TP/SL 调优都重要。

另外三个闸门：

* `max_slippage_bps = 200`：要付的价比起始价差超过 2 分就不做（薄盘保护）
* `max_depth_participation = 0.50`：不超过可见深度的 50%（feed 不提供 size 时该闸门**弃权**，不编数字）
* `max_spot_staleness_s = 30`：现货本身太旧就不判断方向

### 6. 刻意**不**做的两件事

* **不做双边锁利。** 实测 347 个配对市场、3,940 个检查点，**没有任何一刻 UP+DOWN 卖一之和低于 1.00**（最低 1.02），因为 99.77% 的盘口价差 ≥ 0.50。这个套利在你的市场上不存在，详见 `ANALYSIS_REPORT.md`。
* **不设入场价上限。** 我一度想加"价格 > 0.65 就拒绝"，实测**推翻了**：那些成交方向准确率 **98.6%**、是**赚钱**的（市场已把结果定死）。`PriceBandGuard` 默认关闭，要开需显式配置。

## 三、使用方式

### 0. 依赖

```bash
pip install pyarrow          # 读 parquet 需要；只跑 selfcheck 不需要
```

### 1. 自检（不读数据、不联网，先跑这个）

```bash
cd polymarket_sniper
python run_engine.py selfcheck
```

**37/37 通过**。它验证：手续费曲线（并与原研究版 `utils/fee_calculator.py` 逐点比对，误差 < 1e-12）、回看窗口的**前视防护**（决策后再插入 10% 暴涨，决策必须不变）、阈值判定、窗口预热、陈旧拒绝、四个闸门、TP/SL 逐笔顺序判定、结算不收费、方向对错的记账、指标口径分离、实盘 broker 拒绝隐式构造。

### 2. 回测

```bash
python run_engine.py backtest --data ../data
python run_engine.py backtest --data ../data --trades "2026-03-11 (1).parquet"
python run_engine.py backtest --data ../data --assets BTC ETH
python run_engine.py backtest --data ../data --adverse-bps 100     # 更悲观的成交假设
```

输出：终端报告 + `output/engine/ideal_metrics.json`、`ideal_trades.csv`、`summary.json`。

**注意**：`crypto_prices` 只覆盖 2026-03-06 ~ 03-19。对没有现货价的日期运行会得到 0 笔成交——那是**正确的拒绝对齐**，不是 bug。

### 3. 调参

改 `engine/config.json`，或用 `--config` 指向你自己的配置。每个参数在 `config.py` 的 `DEFAULTS` 里都有注释说明"为什么是这个值"。

最值得动的三个：

| 参数 | 默认 | 调整方向 |
|---|---|---|
| `signal.lookback_s` | 180 | 往上调仍有收益，但本质越来越像动量跟随 |
| `exits.stop_loss` | 0.20 | 放宽 → 期望更高、单笔亏损更大；收紧 → 两者反向 |
| `guards.max_quote_staleness_s` | 10 | 实盘数据延迟高就调大；调大会显著降低准确率 |

### 4. paper / 实盘接线

```bash
python run_engine.py paper --data ../data     # 打印接线方式 + 检查数据就绪度
```

引擎**不会自己联网**。要跑实时，你需要自己提供两个对象，然后驱动与回测完全相同的决策路径：

```python
from engine.config import load_config
from engine.backtest import Engine
from engine.dataio import Market, MarketTrades, SpotIndex
from engine.broker import LiveBroker, OrderRequest, OrderSide, Fill

class MyBroker(LiveBroker):
    """用你自己的签名下单客户端实现 submit()。"""
    def submit(self, request: OrderRequest, *, at_price: float) -> Fill:
        ...   # 调用你的 CLOB 客户端，返回真实成交

engine = Engine(load_config(), broker=MyBroker(confirm_live=True))

# 每个新窗口：
signal_spot = SpotIndex("BTC")            # 持续喂入现货价
market = Market(slug=..., asset="BTC", start_ts=..., end_ts=..., outcome="")
prints = MarketTrades(slug=..., by_token={token_up: [...], token_down: [...]})
tokens = (token_up, token_down)

trade, refusal = engine.trade_window(market, prints, tokens)
```

`trade_window()` 完成**完整序列**：算信号 → 过闸门 → 下单 → 逐笔判定 TP/SL 离场。它在 T-120 才动作，其余时间返回拒绝原因，不会空转下单。

**为什么实盘要写代码才能开**：`LiveBroker` 的 `submit()` 是抽象方法且**没有默认实现**，构造时还必须传 `confirm_live=True`。这样"误触实盘"在结构上不可能发生——回测与实盘共用同一条决策路径，唯一区别就是你传进去的 broker。

## 五、已知局限（我不打算掩饰的部分）

1. **只有 1 天样本（792 笔）。** 四种资产混在一起，未分资产验证。动量效应在样本外最易衰减。
2. **入场价用"最后一笔成交价"**，实盘只有吃单能保证这个价位；限价单可能根本不成交。
3. **旧止损的成交假设偏乐观**：回测假设能在触发价成交，薄盘里做不到。`--adverse-bps 50` 是给这个的粗略补偿（净利 10,241 → 9,573，约 −6.5%）。
4. **未计入 gas、资金占用、机会成本。**
5. **`unlabelled_tokens` 431 笔被跳过**：这些市场的两个 token 末期价格太接近，无法可靠区分 UP/DOWN。跳过而不是猜，代价是样本变小。

## 附录 A：为什么放弃"双边锁利"

原设计：等 panic dump，买入暴跌方，再买反向对冲，锁定 `UP+DOWN ≤ 0.95`。在真实数据上：

```
347 个配对市场、3,940 个配对检查点（窗口最后 180 秒）
UP+DOWN 卖一之和:  min 1.0200   median 1.8000
sum <= 0.95 → 0 个检查点 (0.00%)
sum <= 1.00 → 0 个检查点 (0.00%)
```

没有任何一刻低于 1.00。而且退一步说，原设计的"两边各买相同 USDC"**本身也不锁利**：0.30/0.60 各投 100 USDC，UP 赢 +125.6、DOWN 赢 **−41.0**。真正的锁利要求**两边买相同份额**（各 N 份，无论谁赢都收 N），但那个机会在这批数据里不存在。

## 附录 B：手续费口径

```
fee = shares × 0.07 × p × (1 − p)
```

峰值在 `p = 0.5`（每份 1.75 分），两端趋于 0。**结算不是交易、不收费**（本引擎按此处理，selfcheck 有断言）。这也解释了为什么盈亏平衡准确率约等于入场均价 + 手续费：本引擎实测均价 0.7183 → 平衡线 71.83%。
